#218 gate 1: can streamed full backprop at 1B run in 16 GB of RAM?

Date: 2026-11-19, 22:39-23:30. RTX 4050 laptop 6 GB, 16 GB DDR5 (15.29 GiB usable). GPU empty
before every launch (<400 MiB check), one process and one log per run.
GB = 10^9 bytes unless written GiB.

VERDICT
- Yes, but only with the lean state: bf16 master weights with stochastic rounding (SR), bf16
  Muon momentum, 5 parked group inputs in bf16, everything else as #217, 0 DataLoader workers.
- The full-precision design (#216/#217) cannot run here at all. Not only is it short of RAM:
  Windows will not pin more than 6.75 GiB (7.25 GB) for the GPU, and it needs 10.5 GB pinned.
- Lean plan: 5.54 GB pinned + process. Process floor measured at 1.47 GB, so 7.0 GB total.
  Available RAM at rest today: 8.1 GB. Margin 1.1 GB. If the trainer process stays as fat as
  today's (3.07 GB), the total is 8.6 GB: 0.5 GB short at rest, living on Windows trimming idle
  apps (which it did in this session, up to 10.1 GB available).
- Smallest budget: 4.13 GB pinned (adds int8 momentum, bf16 embedding Adam moments) + 1.47 =
  5.6 GB. Margin 2.5 GB at rest. int8 momentum costs a little quality in the proxy.
- Step-time cost of the lean levers: about +0.2 s on a 22.5 s step (~1%). int8 momentum +0.3 s more.
- Quality proxy: SR keeps the update; round-to-nearest does not. On the real 1B group at a
  late-schedule learning rate, SR keeps 99% of the weight update, round-to-nearest 23%, and
  round-to-nearest's held-out loss falls only 43% as far as fp32's. SR ends 0.5-0.9% of the loss
  drop behind fp32; a harmless fp32 control wobbles 0.0-0.45% along the way. This is a 24-step
  synthetic proxy. A held-out LM-loss A/B is still required.

3. QUALITY PROXY ON THE REAL 1B GROUP, LAYERS 4-7 (step 3)
scripts/bench_lean_numerics_218.py. Production layers and stack as #217, deterministic, 8 mb x
4096 tokens, production Muon, per-layer clip 1.0. The group learns to imitate a teacher group
(other seed) on Gaussian inputs; 4 training batches cycled; held-out batch never trained. All
arms start from the same bf16-representable weights. 24 steps per run, Muon lr 0.02 (peak),
0.002 (10% of peak, ~80% into the cosine), 0.0005 (2.5%, ~90% in).
Arms: ref (fp32 master, momentum, park); lean (bf16 SR master, bf16 momentum, bf16 park);
rne (lean with round-to-nearest master: the FALSIFIER); lean_m8 (lean, int8 momentum);
ctrl (fp32 like ref, micro-batch order reversed: a ~1e-7 harmless perturbation, separate runs).

  0.02     0.1028    +0.06%    +0.08%   +0.30%   -0.00% (0.17%)
  0.002    0.0422    +0.48%    +4.3%    +0.48%   -0.01% (0.14%)

Read:
- The falsifier works. Round-to-nearest loses most of each small update (24% kept at 0.0005) and
  its loss stalls. SR keeps it. Had the harness been vacuous (no real rounding, or updates far
  above the bf16 step), rne would match ref; it does not.
- At peak lr, lean's drift from ref is mostly chaos: the fp32 control drifts nearly as far
  (cum_err 0.37 vs 0.49) and the loss gaps are the same size.
- At low lr, SR's per-step noise is as big as the update (0.9-2.5x), so its cumulative error
  starts high and shrinks as the noise averages out (1.40 -> 0.54 over 24 steps). The loss gap
  (0.5-0.9% of the drop) is 2-6x the control's END gap, but lean's mid-run gaps change sign
  (lr 0.0005: +1.5e-4, -1e-6, -6e-5, -1e-6, +6e-5, +1.2e-4). 24 steps cannot tell it from noise.
- The bf16 park alone changes the step-0 gradient by 1.7% (cos 0.99985); Muon turns that into a
  ~20% different first update. The fp32 control shows the same kind of amplification at peak lr.
- int8 momentum is a little worse than bf16 at peak and lowest lr (0.30 vs 0.06%, 1.34 vs 0.90%).
  Use it only if RAM forces it.
Checks: a repeated ref gradient differs by exactly 0; ref recompute == forward (max diff 0.0);
ref in the control processes reproduces ref in the main runs bit for bit; SR is unbiased
(-2.7e-6 relative on a value that round-to-nearest always moves by -1.2e-4). Peak VRAM 4.45 GB
allocated; process working set 7.2-7.6 GB (four arms of host state at once).
THIS IS A PROXY FOR A HELD-OUT LM-LOSS A/B: synthetic objective, 24 steps, one group of 6,
multi-pass over 4 batches. It says the update is not lost. It does not say the model trains as well.

BUILD PLAN (if the maintainer goes ahead)
1. Host state store: one pinned arena (cudaHostRegister, exact size): bf16 masters, bf16 momentum,
   fp32 non-matrix state, fp32 embedding moments, 5 bf16 park slots. Assert arena <= 6.0 GiB and
   process + arena <= available - 1 GB at start; refuse to start otherwise.
2. GPU casts: bf16 -> fp32 after each H2D; SR on write-back with a seed from (step, layer) so a
   resume reproduces it; momentum round-to-nearest.
3. Layer-major driver from bench_streamed_group_217.py; group 1 re-reads the embedding instead of
   parking. Loss + trainable decoder phase; per-layer clip.
4. Checkpoint save/resume and eval from the host arena.
5. Trainer process diet: measure its non-state RAM, target <= 2 GB (0 workers; keep pandas/pyarrow
   out of the training process if only data prep needs them).
6. Tests: streamed == resident over a 3+ step sequence with the bf16 store and the same SR seed
   (bit-identical); must-fail partners (skipped write-back, skipped load); SR unbiased; an RNE
   partner at small lr that must lose >50% of the update.
