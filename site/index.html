Architecture research · single 6 GB GPU

A language model whose memory doesn’t grow.

Transformers remember by keeping every token they have read. HVN keeps a fixed-size state instead — so the cost of the next token is the same at 100,000 tokens as at 100.

The idea

Why constant-cost memory is worth chasing

A standard model’s KV cache grows with every token. Double the context and you double the memory and the work. That is the reason long-context inference is expensive, and it is structural — not an implementation detail you can optimise away.

HVN replaces that cache with a fixed-size state that each new token updates in place, drawing on two ideas: tokens as vortex particles in a velocity field (Lagrangian fluid dynamics), and a state matrix that absorbs new information while discarding noise modes (quantum matrix-product states). The model still reads strictly left to right. It simply stops accumulating.

The finding that reshaped the project

Fitting in memory was never the constraint

Training cost grows as 6 × params × tokens, and a well-trained model needs roughly 20 tokens per parameter. So doubling the model quadruples the work. Memory tricks address about 2× of that gap.

Measured honestly, this hardware’s ceiling is about 142M parameters — not because larger models fail to load, but because they cannot be trained to the point of being worth their size. Every sizing decision since has started from arithmetic rather than from whether the model fits.

The recurring lesson

The number you are watching is usually not the number that matters

The same failure has appeared five separate times, each time with a healthy-looking metric hiding a broken system:

  • A cache served untrained weights for weeks while aggregate loss kept falling.
  • A GPU-graph optimisation published a 6.8× speedup from a test that compared one step against itself — it could not have failed.
  • A verdict was retracted for grading on training loss, which measures memorisation.
  • A code model reached excellent perplexity and scored 0% at actually completing code — the one skill it was built for was 0.02% of its training signal, far too little to register on the curve.
  • A learning rate silently halved on every restart, compounding, invisible to every chart being watched.

The practical rule that came out of it, now enforced before any measurement is taken: if the thing being tested were broken, would this test catch it? Answer it before seeing the result, not after. A test that cannot fail is worse than no test, because it turns a bug into a published number.

Current work

A code-completion model, trained end to end on one laptop

A 48M-parameter model trained on 3.86 billion tokens of source code, using fill-in-the-middle — the model sees the code before and after the cursor and fills the gap, which is what an editor actually needs.

Model size was chosen by measuring time-to-convergence rather than by ambition: a 157M model needs 6.5 days on this hardware, a 48M model 22 hours. A small model trained fully beats a large one trained to 10%.

What the run found

The first attempt reached 63% of its training budget at exactly 0% correct completions — while its loss curve looked healthy. The cause was that the one skill being measured was 0.02% of the training signal: a single token per document asks the model to jump back to the cursor instead of continuing the text it just read. Never learning it costs 0.0006 on the loss curve. No amount of watching that curve could have found this.

After fixing the data recipe — ten times more of that one signal, same compute:

The mechanism works; the model is too small. It reliably knows where to start writing, and it now genuinely reads the code on both sides of the gap. It cannot hold the thread for a whole line — one wrong token fails the entire fill, so 60% per token becomes 1.3% per span. That 1.3% sits against a 1.0% floor for simply copying the previous line, which is to say: at the floor.

This is reported rather than buried because it is the point. A 48M-parameter model is roughly 100× smaller than the code models this task is built for. Perplexity of 4.13 looks excellent and is not evidence of anything — the gate is, and the gate says no.

An earlier reading of this same model, on 50 cases instead of 300, showed 4% — two correct answers. It did not survive the larger sample. It is recorded here because it was briefly believed.
